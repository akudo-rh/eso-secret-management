# OCI の権限・認証に関する検討事項

OpenShift on OCI で ESO を使う場合の、権限と認証方式について確認・決定が必要な事項をまとめる。仕組みと考え方は [README](../README.md) の 5.2 と 6.3 を参照。

## 1. 権限の設計

| No. | 事項 | 内容・現時点の案 | 状況 | 関連 (README) |
|---|---|---|---|---|
| 1 | コンパートメント・Vault・キーの構成 | 環境ごとにコンパートメントを分け、Vault とキーを置く案 | 決定が必要 | 6.3 |
| 2 | アプリ間の分け方 | a (シークレット名)・b (アプリごとの Vault)・c (分けない) から選ぶ。a・b は IAM ポリシーの条件の使い方を確認する | 決定が必要 | 6.3 |

## 2. Workload Identity

| 7 | No. 3 が困難な場合の代替 (Instance Principal) | 権限がノード単位になるため、下表の対策とあわせて評価する | 確認中 | — |

**No. 7 (Instance Principal) を採る場合の論点**

Instance Principal は、ノード (OCI のコンピュート・インスタンス) 自身の ID で認証する方式。鍵の管理は不要だが、権限がノード単位になり、同じノード上のすべての Pod に及ぶ。

| 論点 | 内容 |
|---|---|
| アプリ間の分離 | IAM ではアプリを区別できない (同じノードの ID で取得する)。シークレット名や Vault で分けても、ESO 経由ではすべて読める |
| SecretStore の作成権限 | SecretStore に資格情報を書かなくても接続できるため、作れる人はノードの権限をすべて使える → 作成はプラットフォームチームのみ (RBAC) とし、アプリ間の分離はここで担保する |
| 対象ノードの限定 | ESO を Infra ノード等に寄せ、Dynamic Group をそのノードだけに絞る (タグ等で指定) |
| 他の Pod からの利用 | 同じノード上の他の Pod がメタデータ (169.254.169.254) 経由で同じ権限を使えないようにする通信制御 |
